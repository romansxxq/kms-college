### 1. Порівняння протоколів захисту Wi-Fi

Для WPA2 і WPA3 в таблиці розглянуто режим **Personal**, який використовує пароль мережі.

| Протокол | Алгоритм шифрування | Тип ключа | Основні вразливості |
|---|---|---|---|
| **WEP** | RC4 | Статичний спільний ключ | Короткий вектор ініціалізації та повторення його значень разом зі слабкостями RC4 дозволяють відновити ключ після перехоплення трафіку. |
| **WPA2-Personal** | AES-CCMP | Динамічні сеансові ключі; основою автентифікації є спільний пароль, з якого отримують PSK. | Слабкий пароль можна підібрати офлайн за перехопленим обміном узгодження ключів. |
| **WPA3-Personal** | AES-CCMP; узгодження ключів через SAE | Динамічні ключі, сформовані на основі захищеного обміну SAE. | SAE протидіє офлайн-підбору, але слабкий пароль усе ще можна вгадувати активними спробами підключення; залишаються ризики помилок реалізації. |

У WPA2 **4-way handshake** дозволяє узгодити тимчасові ключі, не передаючи пароль відкрито. У WPA3 механізм **SAE** посилює саме захист узгодження ключів від офлайн-підбору. SAE — це не алгоритм шифрування даних, тому його не слід плутати з AES.

Назви алгоритмів звірено з [документацією Cisco](https://www.cisco.com/c/en/us/support/docs/wireless-mobility/wlan-security/68583-FAQ-Wireless-Security.html) і [HPE Aruba: WPA3-Personal](https://arubanetworking.hpe.com/techdocs/aos/wifi-design-deploy/security/modes/wpa3-personal/); обмеження щодо слабких паролів — з [дослідженням IEEE](https://ieeexplore.ieee.org/abstract/document/11340119).

### 2. Перевірка сертифіката HTTPS-сайту

Використав сертифікат **Telegram Web**, переглянутий у браузері під час попередньої роботи 28.10.2026, як дозволено в умові.

| Поле | Значення |
|---|---|
| Сайт | `https://web.telegram.org/` |
| Кому виданий, Subject | `CN=*.web.telegram.org` |
| Домени в SAN | `*.web.telegram.org`, `web.telegram.org` |
| Ким виданий, Issuer | `C=US, O=GoDaddy.com, CN=GoDaddy TLS Intermediate CA DV - R1v1` |
| Початок дії, Not Before | 12.09.2026 15:53:10 UTC |
| Завершення дії, Not After | 29.03.2027 15:53:10 UTC |
| Алгоритм підпису | **RSA із SHA-256 — sha256WithRSAEncryption** |
| OID алгоритму підпису | `1.2.840.113549.1.1.11` |

Алгоритм підпису перевірив у збереженому сертифікаті, а не визначав за назвою сайту або версією TLS. Він показує, як центр сертифікації підписав сертифікат, і не є назвою шифру для даних самого TLS-з'єднання.

### 3. Рукостискання TLS: шість кроків

Розглядаю звичайне повне рукостискання **TLS 1.3** без клієнтського сертифіката.

1. **ClientHello.** Браузер надсилає підтримувані параметри й свою відкриту частину обміну ключами. Тут починається використання **асиметричної криптографії** для узгодження спільного секрету.
2. **ServerHello.** Сервер обирає параметри й передає свою відкриту частину обміну. Кожна сторона, використовуючи також власний закритий матеріал, обчислює спільний секрет. Сам секрет мережею не передається.
3. **Автентифікація сервера.** Сервер надсилає сертифікат і цифровий підпис `CertificateVerify`. Підпис підтверджує володіння закритим ключем сервера. Ці повідомлення вже захищені **симетричними ключами рукостискання**.
4. **Перевірка сертифіката.** Браузер перевіряє відповідність домену, строк дії, ланцюжок довіри та підписи. Для перевірки цифрових підписів використовується **асиметрична криптографія**.
5. **Finished.** Браузер перевіряє повідомлення завершення сервера й надсилає власне `Finished`. Сторони підтверджують, що узгодили правильні ключі та що обмін не був змінений.
6. **Захищені дані.** Браузер і сервер передають прикладні дані, використовуючи **симетричні ключі трафіку**, отримані зі спільного секрету. Симетричне шифрування підходить для основного обсягу даних, бо працює швидко.

Отже, асиметрична криптографія потрібна для узгодження секрету та перевірки справжності сервера, а симетрична — для захисту повідомлень рукостискання й подальшого передавання даних.

### 4. Підготовка до наступного заняття: мережа малого офісу

Для трьох відділів обрав би керовані комутатори з окремими VLAN, пристрій для маршрутизації між ними, міжмережевий екран і основний та резервний канали до інтернету. Вебсервер потрібно розмістити в окремому сегменті, а доступ між сегментами дозволяти лише за необхідними адресами й портами. Для бездротового доступу потрібне захищене узгодження ключів WPA2/WPA3, а для вебз'єднань — HTTPS із перевіркою сертифікатів.
